# Decisions

This is §2 of the BEA v0.1 design (revision 2), copied verbatim: the fixed decisions (F1–F15) and the integration
decisions (D-INT-1 … D-INT-48) that resolved conflicts between the subsystem designs and the critique findings. The
conflict ids in the last column (C-xx, CT-xx, CI-xx) refer to the design's Appendix A and Appendix C. Changes to frozen
shared files after the freeze are recorded at the end of this file by the integrator (Appendix A.3 of the design).

### Budget decisions

1. **Catalog wire ceiling (D-INT-10): 192 KiB → 320 KiB** (`tests/contracts/catalog-budget.json`; requested by WP1,
   WP4, WP7, WP9, WP11, WP14). Measured with all 37 tools: wire `tools/list` 290,849 B; model-visible 79,718 B (the
   96 KiB ceiling holds); input schemas 58,933 B; output schemas 202,533 B (S6 had estimated 80,876 B). The shared
   result envelope alone is about 66 KB of output schema (about 1.8 KB per tool); the bounded output shapes that the
   2 MiB worst-case envelope test forced on every area make up much of the rest. Output schemas are not model-visible,
   so the token budget the ceilings protect still holds. Meeting 192 KiB would mean cutting about 95 KB of output
   schema across all twelve areas: a contract redesign, not an integration fix. The new ceiling leaves 12.7% headroom.
   Every other D-INT-10 ceiling is unchanged and holds. `measured`/`catalog_sha256` stay null until the release run
   of `npm run catalog:golden`.
2. **Agent bundle budget (DESIGN §5.3, S4 §2.1): 512 KiB → 640 KiB, now enforced by `npm run build:agent`.** The
   integrated agent measures 589,407 B with zero diagnostics. Measured alternatives: `removeComments` 561,444 B (still
   over); compression `terser` 337,171 B, but it mangles names and collapses lines, which S4 §2.1 rejected to keep
   stack traces readable. Largest modules: `hooks.ts` 36.6 KB, `pure/scanEngine.ts` 32.1 KB, `shared/apiProfiles.ts`
   27.0 KB, `dump.ts` 20.6 KB, `hwbp.ts` 20.1 KB; indentation is about 66 KB and retained JSDoc about 26 KB.

### Frida 17.23.2 exceptor deadlock (trace_execution threads mode)

WP9 traced it with stack dumps: `Stalker.follow(tid)` of a thread blocked in a system call arms DR0 at the stub's
return (ntdll `ZwDelayExecution+0x14`); gum's exceptor handles that trap while holding its mutex and allocates; a
contended allocator yields with `SleepEx(0)`, which returns through the same armed address, re-trapping inside the
critical section; the thread blocks forever, and the agent's JS thread at its next guarded read. Mitigation in
`src/agent/trace.ts` (`blockedInStub` + `followAtNextEntry`): when the thread's pc is right after a canonical stub's
`syscall`, an Interceptor listener on that stub follows the thread from its own next entry, so no debug register is
armed. Evidence: `tests/acceptance/integration/traceThreads.test.ts` (24 traces of game_sim's sleeping main thread,
each on a fresh target while threads are being created) passes; against the same build with the deferral disabled it
failed in both runs within the first iterations with `provider_timeout` in `rpc:traceStart`, the reported symptom.
Cost: the thread's first wake-up up to its next entry into that stub is not traced (one frame of a game loop). Still
to report upstream. A separate, older behavior found here (documented in `docs/limitations.md`, not fixed): a second
threads-mode trace of the SAME thread started right after the first records nothing about every other time.

Follow-up (BEA-FEEDBACK item 6, FB-6 below): the workaround's JS listener sat on a stub every thread waits in for the
whole trace. Every wait in the process therefore ran a JS callback under the agent's script lock, and Chrome's GPU
process wedged with 8 threads in the trampoline waiting for that lock. Because Frida applies `Stalker.exclude` only to
direct calls, the followed thread also re-entered that listener under Stalker. The listener is now native and is
detached once its targets are followed.

### Documentation errata (acceptance and release stages)

- **S2 §18.2 / DESIGN §6.2 #14 (WP5):** `map_address` over `pe_path` or in an emulation session, and
  `list_module_symbols` of an emulated module, record and cite the image's `bea.image.pe` summary (observed,
  static-artifact, deduplicated per image digest), so their weakest-parent authority is `static-artifact`; an
  emulation map whose space has no readable module image answers `capability_unavailable(module-file-unknown)`.
- **S4 §11.2 / CT-I4 (WP9):** a read/write debug-register hit's access comes from the accessing instruction's memory
  operand (a read-modify-write is a write), values only when it cannot be decoded; watched bytes covered by an rw slot
  are read with a kernel-side `ReadProcessMemory` copy. The page-guard valve also trips when handling time exceeds 50%
  of a 100 ms window (`busy_pct`, `rate_limited.cause`, `WATCH_RATE_LIMIT_BUSY`).
- **DESIGN §5.3 agent coding rule (WP10, all agent features):** in Frida 17.23.2's QJS on Windows there are no
  infinities (±Infinity, `1/0` and float reads of infinity bits are the canonical NaN), `NaN === x` holds for every
  x, and `Number.POSITIVE_INFINITY` is 1e300. Agent code classifies floats from their bits and compares JS numbers only
  once both are finite. Audited in this stage: `coreRate.ts`, `coreHex.ts`/`coreScalar.ts` and `modifyValues.ts` were
  fixed; the other agent uses of `Number.isFinite` / `isNaN` validate parameters and are unaffected.
- **DESIGN §6.2 #15 / S4 §9 (WP10):** a client-cancelled `scan_memory`/`scan_next` sends the agent `jobCancel` under
  its own 5 s budget and keeps the partial result (`done`, coverage reason `cancelled`); scan float values, input
  words and ordering are decided from bits.
- **S4 §14 "replace" / DESIGN §6.2 #28 (WP12):** replace mode is `Interceptor.replaceFast(target, stub)` with a native
  stub that asks a pinned `decide()` callback per call and either returns the constant or jumps to the original
  (calls with the agent-call bypass, `when` filters and calls after `max_hits` or a stop run the original).
- **DESIGN Appendix A.4, additional rows (WP14):** (1) "no Python → capability_unavailable" reads "no usable Python
  anywhere"; a relative `BEA_PYTHON` is a configuration error at start. (2) bea-emu/0.1 `emu.call` has no deadline, so
  a single call is cut by the per-call watchdog at the bridge deadline (status `timeout`, cause `deadline`), not
  `provider_timeout`. (3) The four unicorn 2.1.4 facts above (S5 §3.7, §3.10, §3.16). (4) The sweep matcher's
  `identity` also matches any function that leaves xmm0 untouched.
- **DESIGN §6.2 #22 (WP13):** a `pe_realigned` dump of an image with a COFF symbol table (gcc/MinGW) carries that table
  byte for byte after `SizeOfImage` (the header points to it); without a readable file the table is dropped
  (`DUMP_COFF_SYMBOLS_DROPPED`).
- **DESIGN §5.9 (WP16):** as recorded for the implement stage, plus: a cancelled call's POST in `--json-response` mode
  never gets a reply (the SDK keeps it pending); in-flight accounting treats it as finished.
- **DESIGN §6.2 #26, #29 (WP11, WP12):** unchanged from the implement stage list above.

### Deviations from the design (bea-emu/0.1 stays wire compatible: additions only)

- **S5 §3.7 (EMU-1):** the ISA guard's tagged site classes gain `sse_inexact`; S5 §4.4 `DeviationKind` gains
  `sse_approx_inexact` (call level, inexact: coverage partial) and `sse_tagging_incomplete` (loader level).
- **S5 §3.8 (EMU-2):** "≤ 1 MiB for single calls, ≤ 4 KiB per buffer per vector in batches" is replaced by "whole
  buffers, at most 56 MiB of out-buffer hex per result, refused up front". The design's caps were silent: the host
  decodes every declared field and read the missing bytes as zeros.
- **S5 §3.6 HLE heap (EMU-6):** the bump allocator becomes a free-list allocator; `DeviationKind` gains
  `hle_heap_exhausted` (call level, inexact). `heap`-placement buffers keep the meaning S5 §7.4 gives them ("heap to
  persist with `save_as`"): they are not freed after their vector.
- **S5 §3.14 (EMU-6):** `BatchResult.summary` gains the optional `stopped {code, message, index, data?}`: a `chain`
  batch whose next vector's buffers cannot be placed ends with the completed prefix (the session holds exactly the
  state after it) instead of an error that discarded the prefix after the state had changed.

The host mirrors of these additions (`src/domain/emuProtocol.ts`, `src/application/emu/deviations.ts`,
`src/domain/evidence/limitations/emulation.ts`, `src/application/diff/hints.ts`, the emulation and diff services) are
owned by the host partitions. Until they map the three new deviation kinds, a result that carries one cannot be
assessed (its limitation sentence is missing).

### Declined or deferred (partition C)

| Suggestion                                                                     | Decision | Reason                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EMU-6 verifier: free each vector's `heap`-placement buffers in `chain` batches | declined | S5 §7.4 gives `heap` placement its meaning: it persists (scratch buffers are the per-vector temporaries). A chain that hands the function a new heap object per vector, which the function links into its state (a list push), would see a freed and then reused block: silently wrong results.
